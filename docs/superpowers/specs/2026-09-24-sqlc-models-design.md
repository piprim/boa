# pgcrud with sqlc-generated models: design

Date: 2026-09-24. Builds on `2026-09-22-pgcrud-design.md` and is compatible with every stage of `2026-09-24-review-cleanup-design.md`; section 7 says where the two meet.

## 1. Goal

Let a struct generated by sqlc (`sql_package: "pgx/v5"`, `emit_db_tags: true`) be used as a pgcrud model, for Select, Insert, Update and Delete, without editing the generated file and without a wrapper struct per table.

Today such a struct fails on three counts, all rooted in the fact that sqlc emits no `bun` tag and no `bun.BaseModel` field:

| Gap | Today | Example on `dao.Mandat` |
|-----|-------|-------------------------|
| Column names | `internal.Underscore(GoName)` | `NbEncaisseNMoins2Year` becomes `nb_encaisse_n_moins2_year`; the column is `nb_encaisse_n_moins_2_year` |
| Table name | `inflection.Plural(Underscore(TypeName))` | `Mandat` becomes `mandats`; `TodoTodo` becomes `todo_todos` instead of `todo.todo` |
| Keys and defaults | nothing is `pk`, nothing is `autoincrement` | `WherePK` fails with "does not have primary keys"; an Insert sends `id = 0` instead of letting the sequence run |

Field types are not a gap. sqlc emits `int`, `string`, `bool`, `[]byte`, `time.Time` and `pgtype.*` values, and every `pgtype` type in the generated models implements `sql.Scanner` and `driver.Valuer`, which `schema.Scanner` and `schema.Appender` already route to. The two exceptions are listed in section 6.

Constraints and assumptions:

- The generated files are never edited. Everything pgcrud needs comes from tags sqlc already emits or from a declaration the application makes at start-up.
- `presence.Of[T]` fields are out of scope for this document (see section 6). They compile and scan today through the `sql.Scanner` path; their unset/null semantics on Insert and Update are a later design.
- The `bun` tag syntax stays the primary way to describe a model. Nothing here changes the behaviour of a struct that carries `bun` tags.
- sqlc version 1.31 naming: `StructName` title-cases each underscore-separated part of a table or column name, `id` becomes `ID`, and tables outside the default schema are prefixed with the schema (`todo.todo` gives `TodoTodo`). No `rename` entry in `sqlc.yaml` is assumed.
- The user commits; the implementation never runs `git commit`. GitNexus impact analysis precedes every symbol edit.

## 2. Approach

Two independent features, each small, plus documentation.

1. **`db` tag as a column-name source.** `schema.Table.newField` reads the `db` tag when the `bun` tag gives no name. This closes the column-name gap for free, since `emit_db_tags` writes the exact column name on every field of every model and row struct.
2. **Table specs registered on the DB.** A `pgcrud.TableSpec` value declares, for one struct type, what a `bun.BaseModel` tag and per-field `bun` options would have declared: table name with schema, alias, and field options such as `pk` and `autoincrement`. It is registered before the type is first used and applied by `schema.Table.init` at the same points where the tags are read today.

Alternatives considered and rejected:

- **Emit `bun` tags from sqlc.** `go_struct_tag` on a `column:` override can attach `bun:",pk"` to one column, and a `column: "*.id"` wildcard could tag every `id`. It cannot emit the table name, since there is no field to hang it on, and it ties the primary-key convention to a glob. Kept as a documented option for the `pk` flag only; the spec mechanism does not depend on it.
- **A `TableNamer` interface implemented by hand-written methods in the generated package.** Works, but puts one hand-written method per table next to generated code and makes the generated package import pgcrud. A registered spec keeps the generated models free of any pgcrud import, confines that import to the one specs file, which the caller may place in another package, and gives sqlc-crud a single slice to emit (section 6).
- **A table-name resolver hook (`func(reflect.Type) string`).** Cannot recover the schema or the digit boundaries from the Go name; the information is not in the type. Rejected.

## 3. `db` tag support

### 3.1 Rule

In `schema.Table.newField`, the SQL name of a field is resolved in this order; the first source that yields a name wins:

1. `bun` tag `column:` option.
2. `bun` tag name (the part before the first comma).
3. `db` tag name: the part of the `db` tag before the first comma. A `db` tag of `-` skips the field, exactly as `bun:"-"` does, but only when the field has no `bun` tag at all.
4. `internal.Underscore(sf.Name)`.

The `db` tag contributes a name only. Options after the comma are ignored, so a `db:"id,pk"` written by hand is not a pgcrud option; use the `bun` tag or a spec for options.

### 3.2 Where

- `processFields` checks `sf.Tag.Get("bun") == "-"` before parsing the tag. It gains the equivalent check for `db:"-"` when the `bun` tag is absent (`Lookup` reports absence, so an empty `bun:""` still counts as present and disables the `db` fallback).
- `newField` receives the `reflect.StructField` already, so the fallback is a `sf.Tag.Lookup("db")` between steps 2 and 4 above. No signature changes.
- The warnings about a tag name that is also an option name apply to the `bun` tag only.

### 3.3 Interaction with embedding

The ambiguity resolution for embedded structs in `processFields` prefers a field whose `Tag` is non-zero. A name that came from the `db` tag leaves `Field.Tag` zero, so two embedded structs that both carry a `db:"id"` field are ambiguous and both dropped, as two untagged `ID` fields are today. This is the existing rule and is not extended to `db` tags.

## 4. Table specs

### 4.1 Type

In the root package:

```go
// TableSpec declares for one model type what its bun.BaseModel tag and
// per-field bun options would declare. It is meant for structs that carry no
// bun tags, such as the ones sqlc generates.
type TableSpec struct {
	// Model is a pointer to the struct type, typically (*dao.Mandat)(nil).
	Model any

	// Name is the table name, optionally schema-qualified: "mandat",
	// "todo.todo". It is what bun:"table:..." declares. Required.
	Name string

	// Alias is the table alias in generated SQL, what bun:"alias:..."
	// declares. Optional; the default stays the underscored type name.
	Alias string

	// Columns maps a column name to the bun field options that column would
	// carry, in bun's option syntax without the leading comma:
	// "pk", "pk,autoincrement", "nullzero,skipupdate", "soft_delete".
	// The keys are column names as resolved by section 3, not Go field
	// names, so they read the same way as the DDL.
	Columns map[string]string
}
```

Column options are given in the `bun` option syntax rather than as typed fields because the option vocabulary is the one `isKnownFieldOption` already validates and the README already documents; a typed mirror of it would be a second vocabulary to keep in step. The table-level values are typed because there are two of them and both are plain strings. The struct is a plain value of strings and maps on purpose: sqlc-crud emits it as a composite literal (section 6) and must not need anything from pgcrud beyond this type.

The `column:` option is not accepted inside `Columns` (the key already is the column) and yields an error at registration.

### 4.2 Registration

```go
// RegisterTable stores the specs and builds their tables at once, so a
// spec that names an unknown column or applies to a type whose table has
// already been built is reported here, not silently ignored later.
func (db *DB) RegisterTable(specs ...TableSpec) error
```

Errors, all wrapping a sentinel so callers can test for them:

- `ErrTableSpecModel`: `Model` is nil, not a pointer, or not a pointer to a struct.
- `ErrTableSpecName`: `Name` is empty.
- `ErrTableBuilt`: the type's table was already built or is being built when the spec arrives. Specs must be registered before the first query on the type; this keeps the rule simple and the registry immutable after use.
- `ErrTableSpecColumn`: a key of `Columns` matches no column of the model, or its options fail `isKnownFieldOption`, or include `column:`.

The registry lives on `schema.Tables` as `specs map[reflect.Type]*tableSpec` under the existing mutex, next to `inProgress`. `Tables.RegisterSpec(typ reflect.Type, spec *tableSpec) error` stores it and calls `Get(typ)`. `DB.RegisterTable` converts each `TableSpec` to the schema form and delegates. The schema form is:

```go
// package schema
type TableSpec struct {
	Name    string
	Alias   string
	Columns map[string]tagparser.Tag // parsed once at registration
}
```

### 4.3 Application

`Table.init` runs `processFields`; the spec is applied inside the same functions that read the tags, so the two sources share one code path:

- **Table name and alias.** After `setName(tableNameInflector(...))` and before `processFields`, `init` looks up the spec. When present it performs what `processBaseModelField` does for `table:` and `alias:`: `schemaFromTagName`, `setName`, and the alias assignment. A struct that has both a `BaseModel` tag and a spec gets the tag's values for the options the tag sets, because `processBaseModelField` runs during `processFields`, after the spec, and overrides whatever it names. Tags therefore win over specs, consistent with the `bun` tag staying the primary description. This precedence is documented on `TableSpec`; specs are for structs without tags, and a struct with both is a configuration smell rather than a supported layering.
- **Column options.** In `newField`, once `sqlName` is resolved (section 3.1), the spec's `Columns[sqlName]` tag, if any, is merged into `tag` before the option checks: every option of the spec entry is added to `tag.Options`, the spec winning on duplicate keys. The rest of `newField` is unchanged, so `pk`, `autoincrement`, `nullzero`, `notnull`, `unique`, `default`, `type`, `soft_delete`, `scanonly`, `skipupdate`, `identity` and the relation options all work through the spec. A relation option in a spec is accepted by the parser but is useless on a sqlc struct, which has no relation fields; it is not special-cased.
- **Embedded structs.** A wrapper such as

  ```go
  type Mandat struct {
  	dao.Mandat `bun:",extend"`
  	Documents  []*Document `bun:"rel:has-many,join:id=mandat_id"`
  }
  ```

  gets the table name and alias from `dao.Mandat`'s spec through the existing `extend` branch, and the `pk` and `autoincrement` flags through the cloned subfields, because the subtable was built by `InProgress(sfType)` with the spec applied. This is the supported way to add relations to a generated model, and it needs no new code.

### 4.4 Example

```go
db := pgcrud.New(pool, pgcrud.WithExecutorResolver(uow.Executor))

err := db.RegisterTable(
	pgcrud.TableSpec{
		Model:   (*dao.Mandat)(nil),
		Name:    "mandat",
		Alias:   "m",
		Columns: map[string]string{"id": "pk,autoincrement"},
	},
	pgcrud.TableSpec{
		Model:   (*dao.TodoTodo)(nil),
		Name:    "todo.todo",
		Alias:   "t",
		Columns: map[string]string{"id": "pk"},
	},
)

var m dao.Mandat
err = db.NewSelect().Model(&m).Where("m.id = ?", id).Scan(ctx)
// SELECT "m"."id", "m"."document_uploaded_id", ... FROM "mandat" AS "m" WHERE (m.id = 42)

_, err = db.NewInsert().Model(&dao.Mandat{...}).Returning("id").Exec(ctx)
// INSERT INTO "mandat" AS "m" ("id", ...) VALUES (DEFAULT, ...) RETURNING "id"
// The zero id is rendered as DEFAULT because autoincrement implies nullzero
// and the Postgres dialect has the DefaultPlaceholder feature.
```

The generated `db` tags give every column its name; the spec gives the table its name and the key its flags. With sqlc-crud emitting the specs (section 6) the two literals above collapse to `db.RegisterTable(dao.PgcrudTables...)`.

## 5. Testing

Unit tests follow the repository rule of one `t.Run` per scenario.

- `schema/table_test.go`, new `TestTableDBTag`:
  - `db` tag names the column when no `bun` tag exists (a field `NbEncaisseNMoins2Year` with `db:"nb_encaisse_n_moins_2_year"`);
  - `bun` name and `column:` option win over a `db` tag;
  - `db:"-"` skips the field; `db:"-"` with a `bun` tag present does not;
  - the part after the first comma of a `db` tag is ignored.
- `schema/table_test.go`, new `TestTableSpec`:
  - name with and without schema sets `Name`, `Schema`, `SQLName` (`"todo"."todo"`) and `SQLNameForSelects`;
  - alias set and default;
  - `pk` and `pk,autoincrement` populate `PKs`, `IsPK`, `NotNull`, `NullZero`;
  - a spec column key that resolves through a `db` tag;
  - `extend` wrapper inherits name, alias and key flags;
  - unknown column, unknown option, `column:` option and empty name are rejected;
  - registering after `Get` returns `ErrTableBuilt`.
- `db_test.go`, `TestRegisterTable`: the `DB` entry point returns the same errors and builds the table.
- `query_test.go`: golden cases for a Select, an Insert with `autoincrement`, an Update by PK and a Delete by PK on a spec-described struct without `bun` tags, including one schema-qualified table. The snapshot files follow the existing numbering.
- `integration_test.go`: one round trip on a table in a non-default schema described by a spec, run only with `PGCRUD_TEST_DSN`.

## 6. Out of scope and follow-ups

- **`presence.Of[T]`.** Scans and appends through `sql.Scanner` and `driver.Valuer` today. What Insert and Update should do with an unset value (omit the column, send DEFAULT, send NULL) and whether `nullzero` should mean "unset" for it is a separate design.
- **Fields pgcrud cannot scan.** `pgtype.Range[T]` implements neither `sql.Scanner` nor a kind `schema.scanner` knows, so a Select that lists such a column fails at scan time; `interface{}` fields (PostGIS geometry in the sqlc output) receive the raw driver value. Both are unchanged by this design. The workaround is a `scanonly` or `bun:"-"` entry in the spec, or a sqlc override to a scannable type.
- **Generating specs with sqlc-crud.** `github.com/piprim/sqlc-crud` is the generator for the specs. It already reads the live catalog to write the CRUD queries sqlc compiles, so the same read knows every table's schema, name, primary key columns and sequence or identity defaults. It gains an output that emits, next to the generated queries, a Go file in the dao package (or a package of the caller's choosing) holding

  ```go
  // Code generated by sqlc-crud. DO NOT EDIT.
  var PgcrudTables = []pgcrud.TableSpec{
  	{Model: (*Mandat)(nil), Name: "mandat", Columns: map[string]string{"id": "pk,autoincrement"}},
  	{Model: (*TodoTodo)(nil), Name: "todo.todo", Columns: map[string]string{"id": "pk"}},
  	// ...
  }
  ```

  so that the application registers every table with one call, `db.RegisterTable(dao.PgcrudTables...)`. Mapping rules for the generator: a column that belongs to the primary key gets `pk`; a key column whose default is `nextval(...)` gets `pk,autoincrement`; an identity column gets `pk,identity`; the struct name follows sqlc's `StructName` so that the `Model` pointer names the type sqlc generated. Hand-written specs stay possible for tables sqlc-crud does not cover. The generator change is sqlc-crud's own work item; this design only fixes the shape it targets.
- **`sqlc` `rename` entries** change Go names but not `db` tags, so they need no support here.
- **Row structs of custom queries** (`VendeurFindByIDRow`) carry `db` tags and can be scanned with `db.ScanRows` or the `SelectQuery` model scanner, but they are not tables: no spec, no `WherePK`.

## 7. Relation to the review cleanup

Stage 4 of `2026-09-24-review-cleanup-design.md` moves `schema.Tables` from the dialect to `DB` and gives `Table` a `tables *Tables` field. This design keeps the spec registry inside `schema.Tables`, which exists in both layouts; only the accessor differs (`t.dialect.Tables()` before stage 4, `t.tables` after). Implement whichever is current when the plan is written; the tests in section 5 do not depend on it. Stage 3 deletes nothing this design uses.

## 8. Open decisions

Recorded so the reviewer can overturn them before the plan is written.

1. **Spec column keys are column names**, not Go field names. Chosen so the spec reads like the DDL and matches what a catalog-driven generator knows. Go field names would avoid the dependency on section 3 resolution.
2. **Specs are immutable after first use** (`ErrTableBuilt`). The alternative, rebuilding the table when a spec arrives late, would invalidate cached `*schema.Table` pointers held by in-flight queries.
3. **Column options reuse the `bun` option syntax** instead of typed fields. Typed fields would be more discoverable in an IDE at the cost of a second option vocabulary.
